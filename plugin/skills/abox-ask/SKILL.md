---
name: abox-ask
description: Asks the user for decisions through question pages on Artifact Box (artifactbox.app) with the `abox` CLI, then waits for the answer they give on the web. Each question carries the work context, background, options, a recommendation and attached artifacts, so someone who knows nothing of the work can decide from the page alone. Use it when the user says to ask through the screen or to keep asking while working ("화면으로 물어봐", "질문 올려 가며 진행해", "결정할 거 있으면 abox로 물어봐"), when project or global instructions say to ask decisions as abox questions ("결정이 필요하면 abox 질문으로 묻는다"), when the user gives a question artifact URL to continue ("이 질문 이어서 진행해"), and when the user says "답했어" after a question was posted. Not for yes/no confirmations, trivial choices (one name, one file), permission or risky-action checks (delete, deploy, push), or what the user already answered in the terminal. Publishing pages and documents themselves is abox-publish. Reporting finished or stopped work to the inbox ("끝나면 알려줘") is abox-report.

# Artifact Box 질문

질문 아티팩트는 정해 가는 대상 하나(주제, 예: 「결제 재시도 설계」)를 담는 아티팩트이고, 그 안에 질문이 `q1`, `q2`…로 쌓인다. 에이전트는 결정이 필요할 때 질문을 올리고 `<URL>#q3` 링크를 사용자에게 준 뒤 `abox wait`로 답을 기다린다. 워크스페이스 멤버는 웹(휴대폰 포함)에서 답한다. 답을 기다리지 않고 작업 완료 · 멈춤 · 실패를 알리는 보고는 `abox-report` 스킬이 맡는다.

이 스킬의 핵심은 질문이 아니라 설명이다. 사용자는 여러 작업을 오가므로 질문만 보고는 무엇을 묻는지 모른다. 질문마다 작업 맥락 · 배경 · 옵션 상세 · 추천 근거와 첨부 아티팩트를 반드시 담아, 그 작업을 전혀 모르는 사람이 요약만 읽어도 큰 그림을 잡고 펼쳐 읽으면 다른 곳을 찾아보지 않고 결정할 수 있게 쓴다. 형식을 줄이거나 칸을 비우는 쪽으로 타협하지 않는다.

## 기본 규칙

- 모든 `abox` 명령에 `--json`을 붙이고 stdout의 JSON 하나를 읽는다. 단, 주제 · 질문을 읽는 `abox read`는 `--json` 없이 Markdown으로 읽는다.
- `abox` 명령은 한 번에 하나씩 실행한다. `;`·`&&`·`$(…)`로 다른 명령과 묶지 않는다.
- 질문 주소(`<URL>#q3`)는 명령에 넘길 때 늘 작은따옴표로 감싼다(`'https://…/a/Xk2…#q3'`). 셸에서 `#`가 주석이 될 수 있다.
- 질문 주소 · 주제 URL을 WebFetch 같은 웹 도구로 열지 않는다. `abox read`로 읽는다.
- **작업 폴더**는 시스템 프롬프트가 세션 전용 임시 디렉토리를 알려 주면(예: Claude Code의 Scratchpad directory) 그 아래 `artifact-box/questions/`, 아니면 `/tmp/artifact-box/questions/`다. 질문 JSON은 여기에 질문마다 새 파일로 쓴다. 작업 디렉토리와 그 하위는 프로젝트 저장소일 수 있으니 파일을 만들지 않는다.
- `abox`는 Artifact Box 서버에 연결해야 한다. 에이전트의 샌드박스가 네트워크를 막는 환경(예: Codex 기본 설정)에서는 `abox` 명령을 네트워크가 열린 권한으로 실행하도록 승인을 요청한다.
- 주제는 **비공개**로 시작한다. **공개(`share`)·삭제(`rm`)는 사용자가 명시적으로 요청할 때만** 한다(아래 '공개').
- **새 주제의 워크스페이스는 사용자가 말할 때만 고른다**(`--workspace`, 고르는 법은 `abox-publish` 스킬의 '워크스페이스'). 말하지 않으면 현재 프로젝트(아래 '1. 주제 정하기')의 워크스페이스, 현재 프로젝트도 없으면 기본 워크스페이스에 새 주제를 만든다. 단, 있는 주제의 첨부를 찾고 게시할 때는 사용자가 말하지 않았어도 **주제의 워크스페이스를 늘 넘긴다**(아래 '3. 첨부 찾기 · 만들기').
- 새 주제에는 미리 만든 태그를 0~3개 붙인다(`abox-publish` 스킬의 '미리 만든 태그'와 같다). 질문을 더할 때는 붙이지 않는다.
- 터미널 답은 **사용자가 실제로 한 답만** `abox answer`로 기록한다. 결정 바꾸기(`--change-decision`)는 사용자가 바꾸자고 할 때만 쓴다.
- 결과의 `warnings`는 이 문서에 없는 코드라도 `message`를 사용자에게 전한다.
- **로그인은 사용자가 직접 한다.** `abox login`·`abox logout`은 어떤 옵션으로도 실행하지 않는다. 사용자가 "로그인해 줘"라고 해도 같다. exit 3(`AUTH_REQUIRED`)이면 아래 문장을 그대로 전하고 멈춘다. `claude -p`·`codex exec`처럼 사용자가 없으면 이 문장을 결과로 남긴다. 사용자가 로그인했다고 하면 멈춘 명령부터 다시 한다. `error.message`가 `ABOX_TOKEN` 환경 변수를 가리키면 이 문장 대신 `error.message`·`error.hint`를 전한다.

  ```
  Artifact Box 로그인이 필요해요. 터미널에서 아래 명령으로 로그인해 주세요.
    abox login
  Claude Code에서는 입력창에 ! abox login 을 입력해도 돼요.
  주소가 나오면 브라우저에서 열어 Google로 로그인하고 승인해 주세요.
  원격 서버라면 그 주소를 아무 기기의 브라우저에서 열면 돼요.
  이미 로그인했는데 이 안내가 나오면, 에이전트를 돌리는 도구(Paperclip 등)가 설정 폴더를 바꾼 경우예요.
  그 도구의 에이전트 환경 변수에 ABOX_CONFIG_DIR=<홈 폴더 절대 경로>/.config/abox 를 넣어 주세요.
  ```

- **`abox` 설치·업데이트도 사용자가 한다.** 설치 스크립트와 `abox update`는 실행하지 않는다. `CLI_UPDATE_AVAILABLE` 경고는 `message`만 전한다. `abox`가 없으면(command not found, exit 127) 아래 문장을 그대로 전하고 멈춘다.

  ```
  Artifact Box CLI(abox)가 설치돼 있지 않아요. https://artifactbox.app/guide 의 설치 명령으로 설치해 주세요(Node.js 24 이상 필요).
  Claude Code 플러그인 · 스킬로 설치하는 방법도 같은 페이지에 있어요.
  이미 설치했다면 ~/.local/bin 폴더가 PATH에 있는지 확인해 주세요.
  설치한 뒤 다시 요청해 주세요.
  ```

## 언제 쓰나

| 언제                                                                            | 무엇을                                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 사용자가 그 세션에서 말함("화면으로 물어봐", "질문 올려 가며 진행해")           | 그 세션 동안 결정이 필요할 때마다 올린다                     |
| 프로젝트 · 전역 지침에 "결정이 필요하면 abox 질문으로 묻는다" 같은 한 줄이 있음 | 말하지 않아도 결정이 필요할 때 올린다                        |
| 사용자가 질문 아티팩트 URL을 주며 이어 가자고 함                                | 아래 '이어 가기'대로 읽고 이어 간다                          |
| 사용자가 "답했어"                                                               | 마지막으로 올린 질문을 `abox wait`로 받는다(아래 '기다리기') |

쓰지 않는 때(화면 질문을 켰어도 터미널에서 묻는다):

- 예/아니오 확인, 이름 하나 · 파일 하나 같은 사소한 선택
- 권한 · 위험 동작 확인(삭제 · 배포 · push)
- 사용자가 이미 터미널에서 답한 것

## 질문 올리기

### 1. 주제 정하기

아래 순서로 처음 맞는 것을 쓴다. 애매하면 터미널에서 한 줄로 확인한다.

1. 사용자가 준 주제 URL
2. 이 세션에서 쓰던 주제
3. `abox ls --type question --project <현재 프로젝트 id> --json`에서 같은 대상을 다루는 주제(제목 · 설명으로 판단). 현재 프로젝트가 없으면 `--project` 없이 워크스페이스 전체에서 찾는다
4. 새로 만든다(아래 '6. 올리기'). 주제 제목은 정해 가는 대상(「결제 재시도 설계」), 설명은 그 주제에서 무엇을 정하는지 한 줄이다

주제 하나에 질문은 100개까지다. 다른 대상의 결정이면 새 주제를 만든다.

**현재 프로젝트**는 `abox-publish` 스킬의 '프로젝트' 순서로 정한 프로젝트의 id다: 사용자가 이번에 말한 프로젝트(`abox project ls --json`의 이름과 맞춰 id로 바꾼다), 아니면 레포 연결(`Artifact Box 프로젝트: <이름> (id: <id>)` 줄)의 id. 둘 다 없으면 현재 프로젝트가 없다. 말한 프로젝트를 찾는 워크스페이스는 그 스킬의 '프로젝트' 1과 같다: 사용자가 말한 워크스페이스, 없으면 레포 연결 프로젝트의 워크스페이스(`abox project info <연결 id> --json`의 `data.workspace.id`), 그것도 없으면 기본 워크스페이스다. 말한 프로젝트가 목록에 없으면 3에서는 `--project` 없이 그 워크스페이스에서 찾고, 새 주제를 만들기로 하면(4) 첨부를 게시하기 전에 `abox project add <이름> --workspace <그 워크스페이스> --json`으로 만들어 그 `data.id`를 쓴다. 레포 연결의 워크스페이스에서 찾았고 그곳이 기본 워크스페이스(`abox workspace ls --json`에서 `default`가 true)가 아니면 만들기 전에 어느 워크스페이스에 만들지 묻는다. 레포 연결 id가 `NOT_FOUND`(exit 4)면 다른 곳에 대신 만들지 않고 알린 뒤 멈춘다.

주제가 정해지면 **주제의 워크스페이스와 프로젝트**를 안다. 다음 단계의 첨부 찾기 · 게시에 쓴다.

- 있는 주제(1~3): `abox info <주제 URL> --json`의 `data.workspace.id` · `data.project.id`다. 이 세션에서 `abox ask`로 만든 주제면 그 결과의 `data.workspace.id` · `data.project.id`를 써도 된다.
- 새 주제(4): 주제를 만들 곳이다. 프로젝트는 현재 프로젝트(없으면 `미분류`)이고, 워크스페이스는 사용자가 말한 `--workspace`, 없으면 현재 프로젝트의 워크스페이스(`abox project info <id> --json`의 `data.workspace.id`), 그것도 없으면 기본 워크스페이스다.

### 2. 한 번에 하나만 묻는다

답 대기인 질문을 여럿 동시에 올리지 않는다. 정할 것이 여럿이면 중요도와 의존성이 큰 것부터 하나씩 묻고, 답을 받은 뒤 다음을 묻는다.

### 3. 첨부 찾기 · 만들기

질문마다 이 결정을 이해하는 데 쓰는 아티팩트를 1~5개 첨부한다(필수). 첨부는 주제와 **같은 워크스페이스**에 있어야 한다. 다른 워크스페이스(개인 ↔ 팀)의 아티팩트는 서버가 「이 워크스페이스에서 찾을 수 없는 아티팩트예요」로 거부한다.

이 단계의 `abox ls` · `abox publish`에는 주제의 워크스페이스를 넘긴다(위 '1. 주제 정하기'의 끝). 있는 주제면 기본 워크스페이스여도 늘 `--workspace <data.workspace.id>`를 넘긴다. 새 주제면 `abox ask`에 넘길 것과 같은 `--workspace` · `--project`를 넘긴다. `--workspace`가 없으면 셋 다 `--project`의 워크스페이스, 둘 다 없으면 기본 워크스페이스에서 동작한다.

1. **찾기**: `abox ls --workspace <주제 워크스페이스> --project <주제 프로젝트 id> --json`(필요하면 `--tag <태그>` · `-q <검색어>`, 없으면 `--project` 없이 같은 워크스페이스 전체)으로 이 결정과 관련된 정의서 · 시안 · 설계 문서 · 리포트를 찾는다. 제목 · 설명으로 맞는지 판단해 맞으면 그 `url`을 그대로 첨부한다.
2. **캔버스**는 관련 보드를 `<URL>#board=<보드 파일>`로 가리킨다. 보드 파일 이름은 이 세션에서 만든 캔버스면 그 `canvas.json`에서, 아니면 `abox pull <URL> --out <작업 폴더>/<새 폴더> --json`으로 받은 `canvas.json`의 `boards[].file`에서 찾는다.
3. **없으면 만든다**: 이 질문을 이해하는 데 필요한 설명을 `abox-publish` 스킬의 규칙으로 만들어 주제와 같은 워크스페이스 · 프로젝트에 게시한 뒤 첨부한다(`abox publish … --workspace <주제 워크스페이스> --project <주제 프로젝트 id> --json`). 글 · 표 · 비교면 Markdown, 화면이 걸린 결정이면 캔버스 시안, 차트가 필요하면 HTML이다. 새로 만든 아티팩트는 일반 아티팩트라 다음 질문에서 다시 붙인다.
4. 질문 아티팩트(자기 주제 포함)는 첨부할 수 없다. 앞 결정은 `related`로 가리킨다. 바깥 웹 문서는 첨부가 아니라 `links`에 둔다.
5. 관련 없는 아티팩트를 개수를 채우려고 붙이지 않는다.

**첨부 `note`**(1~200자, 한 줄)는 「이 첨부에서 무엇을 보면 되는지」를 구체적으로 쓴다.

- 좋은 예: 「3절 『실패 유형』 표에서 일시 오류의 비율」, 「B안 보드의 결제 결과 알림 화면」
- 쓰지 않는 예: 「참고 자료」, 「관련 문서」, 「설계 문서」

### 4. 질문 쓰기

1. **종류를 고른다**: 옵션 중 하나를 고르게 하면 `choice`(객관식), 값이나 글로 답하게 하면 `open`(주관식), 제안 하나에 동의를 구하면 `opinion`(동의 구하기)이다.
2. **틀을 받는다**: `abox ask --example <choice|open|opinion> --json`의 `data`가 그대로 통과하는 질문 JSON이다. 칸 구성과 분량을 참고하되 예시 내용(결제 재시도 등)을 옮기지 않는다. 예시의 첨부 주소(`EXAMPLE0…`)와 바깥 링크는 자리만 채운 것이라 실제 값으로 바꾼다.
3. **작업 폴더에 새 파일로 쓴다**: `<작업 폴더>/<주제를 나타내는 이름>-q<번호>.json`(예: `payment-retry-q3.json`). 칸마다 무엇을 쓰는지와 한도는 **`references/question-json.md`**에 있다.
4. **쓰는 법**
   - 모든 필수 칸을 성실히 쓴다. 길이를 줄이려고 설명을 빼지 않는다. 질문 하나가 수천 자가 되어도 된다.
   - 요약 칸(`work.goal` · `title` · `background.decide` · `background.summary` · 옵션 `title` · `summary` · `recommend.reason` · 동의 구하기 `reasons`)은 상세를 읽지 않아도 큰 그림이 잡히게 따로 쓴다. 상세 칸의 첫 문장을 그대로 옮기지 않는다.
   - 작업 맥락(`work`)은 질문마다 쓴다. 이 질문만 열어 본 사람도 어느 작업의 무엇인지 알아야 한다.
   - 옵션 `summary`는 그 옵션이 다른 옵션과 무엇이 다른지(무엇을 얻고 무엇을 내주는지) 한두 문장으로 쓴다.
   - 추천은 근거(`why` · `points`)와 다시 검토할 조건(`revisit`)까지 쓴다.
   - 이미 주제에 있는 결정은 `related`로 가리킨다(주제에 있는 번호만, 새 주제의 q1은 비운다).
   - 처음 보는 사람이 모를 낱말(약어 · 내부 이름 · 외부 서비스)은 `terms`에 푼다.
   - 비유 대신 조건과 수치로 쓴다(「느리다」가 아니라 「p95 2초를 넘는다」).
   - 질문 글은 화면과 같은 해요체로 쓴다.
   - `label`(24자 이하)은 결정 목록 · 알림에 쓰는 짧은 이름이다(「재시도 위치」).

### 5. 올리기 전 점검 (맥락 없는 사람 점검)

질문 파일을 다시 읽고 아래가 **모두 「예」일 때만** 올린다. 하나라도 「아니오」면 고친 뒤 처음부터 다시 점검한다.

- [ ] 요약층(작업 목표 · 질문 · 정할 것 · 배경 요약 · 옵션 요약 · 추천 한 줄)만 읽어도 무엇을 · 왜 정하는지와 추천이 보인다
- [ ] 이 작업을 전혀 모르는 사람이 무슨 작업인지 안다(`work`)
- [ ] 왜 지금 이 결정이 필요한지, 무엇이 이 결정을 기다리는지 안다(`work.blocks`)
- [ ] 지금 상황과 이번에 정할 것을 안다(`background`)
- [ ] 각 옵션이 무엇을 뜻하는지, 고르면 무엇이 바뀌는지 안다(옵션 상세)
- [ ] 추천과 그 근거, 다시 검토할 조건을 안다(`recommend`)
- [ ] 처음 보는 낱말이 모두 풀려 있다(`terms`)
- [ ] 첨부마다 무엇을 보면 되는지 적혀 있고, 첨부가 이 결정과 관련 있다
- [ ] 섹션을 펼쳐 읽고 첨부를 보면 다른 곳을 찾아보지 않아도 결정할 수 있다

### 6. 올리기

새 주제(q1)는 `--title` · `--desc`가 필수이고, `--dir` · `--repo` · `--tag` · `--workspace`는 `abox-publish` 스킬의 '새 게시'와 같은 규칙으로 채운다. `--project`에는 현재 프로젝트의 id를 넘기고, 없으면 넘기지 않는다(`미분류`).

```bash
abox ask <작업 폴더>/payment-retry-q1.json \
  --title "결제 재시도 설계" --desc "결제가 일시 오류로 실패할 때 다시 시도하는 방법을 정해요" \
  --project Pq4wT8nV2mK6rX9bL3cH7j --dir payment-service --repo hodoolabs/payment-service \
  --tag 설계 --json
```

있는 주제에 더할 때는 `--url`만 준다(`--title` 등 주제 정보와 `--workspace`는 함께 줄 수 없다).

```bash
abox ask <작업 폴더>/payment-retry-q4.json --url https://artifactbox.app/a/Xk2vR9pQ7mL4tB8nC1dE5f --json
```

앞 질문을 이어받는 새 질문(의견을 반영한 수정안, 고친 질문)은 `--revises <번호>`를 더한다. 대상이 답 대기 · 논의 중일 때만 된다. 결정된 질문은 사용자가 결정을 바꾸자고 할 때만 `--revises <번호> --change-decision`으로 대체한다.

```bash
abox ask <작업 폴더>/payment-retry-q5.json --url https://artifactbox.app/a/Xk2vR9pQ7mL4tB8nC1dE5f --revises 3 --json
```

새 질문도 모든 칸(작업 맥락 · 첨부 포함)을 채우고 '5. 올리기 전 점검'을 거친다. 올린 질문의 본문 · 첨부는 고칠 수 없다. 바꾸려면 대체한다.

### 7. 알리기

결과의 `data.questionUrl`과 `data.label`로 사용자에게 한 줄을 준다(주소는 줄이지 않는다).

```
q3 재시도 위치 — https://artifactbox.app/a/Xk2vR9pQ7mL4tB8nC1dE5f#q3
```

새 주제를 만들었으면(`data.created`) 비공개로 만들었다는 것과 워크스페이스(`data.workspace.name`, 팀이면 "비공개지만 {팀 이름} 멤버 모두 볼 수 있어요") · 프로젝트(`data.project.name`)를 함께 알린다. 이번에 `abox project add`로 프로젝트를 만들었으면 "새 프로젝트를 만들었어요: X"라고 알린다. 대체했으면(`data.revises`) `q3 → q5`를 덧붙인다. 그 뒤 바로 '기다리기'로 간다.

## 기다리기

`abox wait '<URL>#q3' --minutes <분> --json`은 답이 오면 바로 끝난다. 답 · 대체 · 거둠 · 시간 만료 모두 exit 0이고 `data.result`가 결과를 가른다(`answered` · `closed` · `waiting`). 연결이 끊기면 마감까지 알아서 다시 연결한다.

에이전트마다 기다리는 법이 다르다.

| 에이전트                                                  | 방법                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Claude Code(Bash 도구에 `run_in_background`가 있음)       | `abox wait '<URL>#q3' --minutes 115 --json`을 **백그라운드**(`run_in_background: true`)로 실행하고 "답을 받으면 이어서 진행할게요"라고 알린 뒤 턴을 끝낸다. 명령이 끝나면 Claude Code가 다시 부른다. 결과가 `waiting`이면 같은 명령을 다시 백그라운드로 걸고 턴을 끝낸다 |
| Codex 등(백그라운드 명령이 끝나도 에이전트를 깨우지 않음) | **앞에서** `abox wait '<URL>#q3' --minutes 15 --json`으로 기다린다(10~20분, 셸 도구의 시간 제한은 그보다 길게 잡는다). `waiting`이면 "답하면 '답했어'라고 알려 주세요"와 다음에 실행할 명령을 남기고 턴을 끝낸다. 사용자가 "답했어"라고 하면 `--minutes 1`로 다시 부른다 |

사용자가 "답했어"라고 하면 어느 에이전트든 마지막으로 올린 질문을 `abox wait '<URL>#q3' --minutes 1 --json`으로 받는다.

## 답을 받은 뒤

| 결과                      | 할 일                                                                                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `answered` · `decided`    | "q3 결정: B. 큐 워커에서 재시도"처럼 결정(의견이 있으면 의견도)을 알리고, 그 결정대로 작업을 이어 간다. 다음 결정이 필요하면 다음 질문을 올린다                                                 |
| `answered` · `discussing` | 의견(`answer.text`)을 반영한 새 질문을 써서 `--revises <번호>`로 올린다. 의견이 이미 결정을 담고 있어도(「B로 하되 간격은 1분」) 임의로 결정하지 않고 반영한 질문으로 다시 묻는다               |
| `closed` · `superseded`   | 같은 질문을 다시 올리지 않는다. `abox read '<URL>#q<supersededBy>'`로 이어받은 질문을 읽고, 답 대기면 그 질문을 기다린다                                                                        |
| `closed` · `withdrawn`    | 같은 질문을 다시 올리지 않는다. 거둬들였다는 것과 이유(`withdrawal.reason`)를 사용자에게 알리고, 그 결정 없이 진행할 수 있는지 터미널에서 묻는다                                                |
| `waiting`                 | 위 '기다리기'대로 다시 기다리거나 턴을 끝낸다                                                                                                                                                   |
| exit 4                    | 기다리는 동안 주제 · 질문이 지워졌거나 워크스페이스에서 빠졌다. 그 결정은 터미널에서 묻는다                                                                                                     |
| exit 6                    | 마감까지 서버의 응답을 한 번도 받지 못했다(연결 실패 · 서버 오류 · 일시 거절). 샌드박스가 네트워크를 막아서라면 승인을 요청해 다시 실행하고, 아니면 `error.message`와 다시 기다릴 명령을 알린다 |

## 터미널 답 · 결정 바꾸기 · 거두기

- **터미널에서 답함**: 질문을 올린 뒤 사용자가 터미널에서 답하면("B로 해") 그 답을 그대로 기록한다. 기다리던 `abox wait`도 이 답으로 끝나므로 같은 결정을 두 번 반영하지 않는다.

  | 종류        | 명령                                                                                                   |
  | ----------- | ------------------------------------------------------------------------------------------------------ |
  | 객관식      | `abox answer '<URL>#q3' --option B [--text "<사용자가 한 말>"] --json` · 옵션 없이 의견만: `--text`    |
  | 주관식      | `abox answer '<URL>#q3' --text "<답>" --json`                                                          |
  | 동의 구하기 | `abox answer '<URL>#q3' --agree [--text "<의견>"] --json` · 다른 의견: `--disagree --text "<다른 점>"` |

  `QUESTION_CLOSED`(exit 1)면 웹에서 먼저 답했거나 닫힌 것이다. `error.status`·`error.answer`(답한 사람 · 출처 · 시각)를 사용자에게 보이고, 먼저 저장된 답을 따른다.

- **결정 바꾸기**: 사용자가 "q3은 A로 바꾸자"처럼 결정을 바꾸자고 할 때만 한다. 바뀐 결정을 설명하는 새 질문(모든 칸)을 써서 `--revises 3 --change-decision`으로 올린다. 사용자가 이미 고른 답이면 올린 새 질문에 바로 `abox answer`로 그 답을 기록하고 이어 간다.
- **거두기**: 작업 방향이 바뀌어 필요 없어진 질문(답 대기 · 논의 중)은 `abox withdraw '<URL>#q3' --reason "<이유>" --json`으로 거둔다. 기다리던 `abox wait`는 `CLOSED … 거둬들임`으로 끝난다.

## 이어 가기

다른 세션에서 사용자가 주제 URL을 주거나, 이 세션의 주제를 다시 볼 때:

1. `abox read '<주제 URL>'`로 결정 목록 · 진행 중 질문 전체 · 지난 질문을 Markdown으로 읽는다. 결정된 질문의 전체 내용은 `abox read '<URL>#q5'`로 읽는다.
2. 답 대기 질문이 있으면 그 번호로 '기다리기'를 한다. 논의 중 질문이 있으면 '답을 받은 뒤'의 `discussing`대로 한다.
3. 결정들을 작업에 반영하고 이어 간다. 다음 질문은 같은 주제에 `--url`로 올린다.

## 공개

사용자가 주제를 공개해 달라고 할 때만 한다.

1. 첨부도 함께 공개할지 한 줄로 묻는다: "첨부 n개는 비공개라 받는 사람에게 '열 수 없는 첨부예요'로 보여요. 첨부도 같은 기간으로 공개할까요?" 첨부 목록은 `abox read '<주제 URL>' --json`의 `data.topic.allAttachments[]`(`shareActive: false`가 비공개)다.
2. 주제를 `abox share <주제 URL> [--expires 1d|7d|30d|never] --json`으로 공개한다(기본 7일).
3. 동의했으면 비공개 첨부마다 `abox share <첨부 id> --json`으로 공개한다. 주제에 `--expires`를 줬으면 첨부에도 같은 값을 준다.

받는 사람은 질문과 결정을 볼 수만 있고 답할 수 없다. 공개 내리기 · 삭제는 `abox-publish` 스킬의 '공유·관리'와 같다.

## 실패 처리

실패하면 stdout에 `{"ok":false,"error":{"code","message","hint"?,…}}`가 나온다. exit code로 판단하고, `error.hint`가 있으면 사용자에게 함께 전한다.

| exit · `error.code`                    | 뜻                                                                         | 할 일                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2 · `QUESTION_INVALID`                 | 질문이 형식에 맞지 않거나 첨부 · `related`가 맞지 않음                     | `error.issues[]`의 `path`(질문 JSON 안의 JSON Pointer: `/options/1/detail/how` = 둘째 옵션의 `detail.how`)를 `message`대로 고쳐 다시 올린다. 칸을 지우거나 비워서 통과시키지 않는다. 첨부 문구별 처리는 `references/question-json.md`의 '첨부'. 같은 오류(`path`·`code`가 같은 이슈)가 3번 반복되면 멈추고 `issues`와 질문 파일 위치를 사용자에게 알린다 |
| 2 · `MISSING_REQUIRED`                 | 새 주제에 `--title` · `--desc`가 없음                                      | 채워서 다시 실행                                                                                                                                                                                                                                                                                                                                         |
| 2 · `INVALID_INPUT`                    | 사용법 오류, 질문 아티팩트가 아닌 URL, 질문 종류에 맞지 않는 `answer` 옵션 | `error.message`대로 고친다. 종류가 맞지 않으면 `abox read '<URL>#q3'`로 종류를 확인한다                                                                                                                                                                                                                                                                  |
| 2 · `INVALID_INPUT` + `candidates`     | 같은 이름의 워크스페이스가 여럿                                            | 후보를 보여 주고 고르게 한 뒤 `--workspace <id>`로 다시 실행                                                                                                                                                                                                                                                                                             |
| 1 · `QUESTION_CLOSED`                  | 그 질문이 더는 그 동작을 받지 않음                                         | `error.status` · `answer` · `supersededBy` · `withdrawal`이 지금 상태다. 결정됐으면 그 결정으로 이어 가고, 대체됐으면 이어받은 질문을 읽고, 거둬들였으면 다시 올리지 않는다. 결정된 질문을 대체하려던 것이면 사용자가 결정을 바꾸자고 했을 때만 `--change-decision`을 붙인다                                                                             |
| 3 · `AUTH_REQUIRED`                    | 로그인 필요                                                                | `abox login`을 실행하지 않고 '기본 규칙'의 문장을 안내한 뒤 멈춘다                                                                                                                                                                                                                                                                                       |
| 4 · `NOT_FOUND`                        | 주제 · 질문 · 프로젝트 없음, 멤버가 아님                                   | 주소를 확인한다. `abox wait` 중이었다면 지워진 것이니 그 결정은 터미널에서 묻는다. 레포 연결의 프로젝트가 없으면(「프로젝트가 없어요」) 다른 곳에 대신 만들지 않고 알린 뒤 멈춘다                                                                                                                                                                        |
| 5 · `LIMIT_EXCEEDED`                   | 질문이 128KB를 넘음, 또는 주제의 질문이 100개                              | 크기면 긴 설명을 첨부 아티팩트(Markdown)로 옮기고 질문에는 요약과 결정에 필요한 핵심을 남긴다. 개수면 새 주제를 만든다                                                                                                                                                                                                                                   |
| 6 · `NETWORK_ERROR` · `INTERNAL_ERROR` | 서버 연결 실패 · 서버 오류                                                 | 샌드박스가 네트워크를 막아서라면 승인을 요청해 다시 실행. 아니면 한 번 다시 실행한다. `ask`를 다시 보내기 전에는 이미 올라갔는지 확인한다(새 주제면 `abox ls --type question -q <주제 제목> --json`(현재 프로젝트가 있으면 `--project <id>`도), 있는 주제면 `abox read '<주제 URL>'`). 또 실패하면 `error.message`·`error.hint`를 전하고 멈춘다          |
